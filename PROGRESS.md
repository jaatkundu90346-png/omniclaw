## 2026-10-12 — Bug hunt after the bots removal: 12 frontend defects found, 9 fixed
- **Method:** two subagents audited in parallel — one over `web-next/` (dangling imports/CSS, removed-store-field references, leaks, null risks) and one over `server.js` + `src/core` (dangling refs, undefined identifiers, route shadowing, config keys). My first version of this test used a `baseline + 1` tolerance and passed against the BROKEN code — a test that proves nothing. Tightened to `after <= baseline`.
- **Silent data loss:** `main.js` onSend set `location.hash` and then immediately tested `if (thread)` — but `hashchange` is queued as a task, so `thread` was always still null and the typed message, its attachments and its workspace path were dropped. ## 2026-09-27 — Long-task budget, take 2: the token ceiling, not the round ceiling, was the wall
- **Symptom (user, verbatim):** "wahi problem exact problem" — after the round-budget fix, the same NEXUS task still stopped, this time on run 3 (`run_1790495242489_3h4x4u`, message "continue") with `finalMetadata.stopReason: "budget-exhausted"` after 15 steps, and the agent's own summary said "tool budget khatam ho gaya — isliye ab koi aur call nahi kar sakta."
- **Why the round fix was not enough:** the run cleared the 18-round wall and hit the SECOND ceiling. The run token budget default is 600k, and this endpoint has no prompt caching (server log: "no caching (No documented prompt-caching route for this endpoint)"), so every round re-sends the whole ~57k-char context. Empirically 600k is gone in ~15 rounds — i.e. the default is calibrated for a short task in exactly the same way the 18-round default was. Giving a 7-step plan 48 rounds therefore bought nothing.
- **Fix:** `longTaskTokenBudget` (omni-loop.js) scales the default the same way as rounds: `600k + (steps - 2) * 300k`, clamped at the existing 2M ceiling. A 7-step plan now gets the full 2M, a 4-step plan 1.2M. An explicit `runtime.omniLoop.runTokenBudget` still wins, and the clamp ceiling is unchanged.
- **Bug I introduced and caught before shipping:** the telemetry write (`report.longTaskBudget = ...`) sat BEFORE `const report = {`, so it would have thrown a TDZ ReferenceError inside the surrounding try/catch and silently skipped the ENTIRE budget block — a fix that does nothing while looking present. The decision is now computed early into `longTaskBudgetMeta` and published after `report` exists. The smoke asserts the live loop actually granted 48 rounds / 2M tokens, so this class of "present but inert" failure cannot pass again.
- **Verified:** `test:long-task` extended to 26 assertions ALL PASS (round math, token math, the live loop applying both, resume handoff, plan-less run untouched). Regression PASS: omni-loop, plan-resume, agent-loop. Server restarted, health 200.
- **Honest limit, unchanged:** a plan big enough to exhaust even 2M still stops — but the stop now hands off the open steps, so "continue" resumes instead of restarting. Raising the clamp further would need a real per-round cost measurement, which I did not invent.

## 2026-09-27 — Unblock contract: the "Thinking...(6)" loop had a harness cause, not a model cause
- **Symptom (live run `run_1790492275263_vajwt0`, session `..._v51stl`, project myNew folder):** UI sat in "Thinking… (6)" while the agent probed `Test-Path .\node_modules` again and again. Replay of the run's own toolOutputs gave the two causes, both harness gaps:
  1. `npm install` hit a real `ENOTEMPTY` error and the model (correctly) tried to recover; the shell then blocked `Remove-Item .\node_modules -Recurse -Force` and returned **only the raw regex** — no instruction. The model had nothing to act on, so it kept nudging. (The command was valid PowerShell; my first read of the screenshot as a `\Recurse` typo was wrong, and the hint was corrected rather than shipped.)
  2. Two `exec` calls returned `{"status":"started","processId":…}` — a **pid, not a result** — because long commands are backgrounded. The tool that reads them, `process_status`, lives in the `computer` toolset, which a website task never loads. So the model *could not check its own background process* and fell back to filesystem polling + thinking. This is the real spin.
- **Fix 1 — a block must teach.** New `shellBlockHint` (shell-policy.js) + `FIX:` line in the blocked-command error. Hints name the safe alternative: recursive delete → ask the user or `delete_computer_path`; `Stop-Process -Name node` → that kills OmniClaw itself (we run on node), use `process_kill`; plus git reset/clean, disk format, shutdown, bash `rm -rf`. **The block itself is unchanged** — only the feedback.
- **Fix 2 — a backgrounded exec must be checkable.** `annotateBackgroundProcess` (omni-loop.js) runs on every shell observation: when the output carries a `processId` + started/running status it (a) admits `process_status` into the live menu via the existing `admitMenuMissTool`, (b) returns `stillRunning: true` + a `nextStep` naming the exact follow-up call and telling the model not to guess or poll, (c) records it in `report.backgroundProcesses` and emits a `model_tool_loop.background_process_started` event. A foreground exec is left untouched.
- **Verified live:** replaying the exact blocked command through the real `ShellExecutor` now returns the `FIX:` line naming `process_kill` + `delete_computer_path`. `test:unblock` (new, 20 assertions) ALL PASS; regression PASS: omni-loop, agent-loop, tool-call-parse, control-commands, shell-repair, process-status, pipeline-audit, health smoke.
